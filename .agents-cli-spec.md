# Agent Spec — Collegentic

Hackathon: Google Cloud "All Things Agentic Hackathon" — Taskmaster track.

## Overview

Collegentic is an autonomous college-application taskmaster. A student tells it which
colleges they're applying to (natural language or a short list); a multi-agent system
then researches each college's real requirements from official sources, normalizes them
into a structured model, detects conflicts across schools (recommendation types, deadline
clustering, testing, financial aid), matches the student's existing essays/materials to
new prompts, scores and explains task priority, computes an explainable per-college
readiness score, and keeps a dashboard + task list up to date — asking for human approval
before any action that could materially change the student's plan or overwrite
user-authored content.

It is not a chatbot with a research button. The demo path is:
**goal → plan → research → analyze → compare → create tasks → prioritize → update
state → ask for human input when needed.**

Full behavioral spec (product requirements, UI layout, scoring formulas, page-by-page
detail) was supplied by the user in the initiating conversation turn and is treated as
binding; this document is the technical distillation used to drive scaffolding and
implementation. Where this doc is silent on a detail, the original conversation turn is
authoritative.

## Example Use Cases

1. **Cold start.** Student enters "I'm applying to MIT, Princeton, Stanford, Rice, and UT
   Austin." Orchestrator parses 5 college names, checks which are already tracked (none),
   and kicks off the intake pipeline for all 5. Within the run: each college is researched
   from official sources, requirements are normalized and stored with source citations, a
   recommendation conflict is found (0 recommendations on file vs. 4 schools requiring 2
   each with different preferences), essay matches are computed against the student's
   existing Common App essay, tasks are generated, priorities are scored, readiness scores
   are computed, and the dashboard reflects all of it. Agent Activity shows each step.

2. **Demo Mode.** Judge clicks "Try Demo Mode" with zero data entry. A pre-built fictional
   student profile (6 colleges, partial essays, mixed recommendation status, at least one
   stale/uncertain research source, overlapping essay prompts, a real recommendation
   conflict) is seeded into Firestore under a demo user and the dashboard loads populated.

3. **Incremental add.** Student who already has 3 tracked colleges adds a 4th. Orchestrator
   identifies it as the only new college, researches only that one (existing 3 are read
   from Firestore, not re-researched), and re-runs conflict/priority/readiness analysis
   with the new college included.

4. **Uncertain research.** Official page for a school's recommendation policy is unclear.
   Research/Requirements agents mark that requirement `confidence: low`, attach the
   secondary source used, and surface "⚠ Verification recommended" — they do not invent a
   number of recommendations required.

5. **Partial progress, no upload.** Student tells the Student Advisor "I've started my MIT
   essay, it's about half done." This updates essay `completionPercentage` and `status`
   via a normal (non-inferred, user-asserted) write — no file required.

6. **Human-in-the-loop.** Task Planning Agent wants to mark a requirement "Complete" based
   only on inferring it from conversation, not explicit confirmation. This is written as a
   `pendingActions` doc requiring the student's explicit Approve before the requirement
   status actually changes.

7. **Advisor Q&A.** Student asks "Why is the Princeton essay high priority?" Student
   Advisor Agent reads already-stored priority score + explanation from Firestore and
   answers — it does not re-run research or re-score live.

## Tools Required

All tools are plain Python functions passed to `LlmAgent(tools=[...])`, following the ADK
"function tool" pattern (see `deep-search/app/agent.py`, e.g. `emit_expense_alert` in
`ambient-expense-agent`). No MCP server needed for MVP.

- **`google_search`** (ADK built-in) — used only by the College Research Agent (and,
  minimally, by the Orchestrator for college-name disambiguation, mirroring
  `deep-search`'s `plan_generator` "search only to disambiguate, never to investigate"
  rule). No other agent gets this tool.
- **Firestore read/write tools** (`google-cloud-firestore` client, ADC on Cloud Run) —
  one thin module (`app/tools/firestore_tools.py`) exposing typed functions:
  `get_tracked_colleges`, `get_college`, `save_college`, `save_requirements`,
  `get_requirements(college_ids)`, `save_research_sources`, `get_student_materials`,
  `save_essay_matches`, `get_tasks`, `save_tasks` (dedupe-aware), `save_conflicts`,
  `save_readiness`, `save_recommendation`, `get_recommendations`, `create_pending_action`,
  `resolve_pending_action`, `log_agent_run` (start/update/complete — powers Agent
  Activity). Every write tool validates its payload against the matching Pydantic schema
  before writing — agents cannot silently write malformed or partial documents.
- **Scoring functions** (plain Python, no LLM) — `compute_priority_score(...)` and
  `compute_readiness_score(...)` implementing the explainable weighted formulas from the
  spec (deadline urgency, workload, dependency pressure, requirement importance,
  progress). These are deterministic and unit-testable; the LLM agents that wrap them only
  generate the natural-language explanation from the already-computed numbers. This
  mirrors `ambient-expense-agent`'s "business rules in code, LLM for judgment" split.
- **Auth**: no user-facing OAuth in this phase (explicitly deferred). Backend uses ADC for
  Gemini (Vertex) and Firestore. No third-party API keys required beyond
  `GOOGLE_API_KEY`/Vertex credentials.

## Constraints & Safety Rules

- Never invent a requirement, deadline, or source. Missing/unclear data is represented as
  `status: "needs_verification"` / `confidence: "low"`, not a guessed value.
- Every stored `Requirement` must carry at least one `sourceId` once research has run on
  it; requirements with zero sources are allowed only in the `not_researched` state.
- Research prioritizes official sources (admissions/financial-aid/department pages) over
  secondary sources; secondary-source use must be flagged `official: false` in the UI.
- Agents never submit an application, submit an essay, fabricate a student
  accomplishment, claim a requirement is satisfied without evidence, or send external
  communication (email, etc.) — none of these tools exist in this system at all.
- Only the Essay Matching Agent reasons about essay content, and only to score
  reuse-fit — it never rewrites, edits, or coaches. No agent has an "edit essay" tool.
- Autonomous-OK: research, requirement extraction, conflict detection, essay matching,
  priority scoring, readiness scoring, task generation.
  Requires human approval via `pendingActions`: marking a requirement/essay "Complete" or
  "Submitted" based only on agent inference (vs. explicit user statement), any Task
  Planning action that would delete or overwrite a user-authored `StudentMaterial`, and
  any bulk plan change (e.g., "adopt this recommendation-request plan across 4 schools").
- Student Advisor Agent has read-only Firestore tools and no `google_search` — it explains
  stored state, it does not re-research or infer new facts live.
- Cost control: default model for every agent is `gemini-3.6-flash` (never a
  pricier/older model without explicit ask). Research is cached in Firestore and re-run
  only when a college is new, explicitly refreshed by the user, or an agent's own
  confidence check fails. Iterative research refinement loop is capped (2 iterations, not
  5 — cheaper than the `deep-search` default, justified by narrower per-college scope).
- Secrets: `GOOGLE_API_KEY` / GCP credentials only via `.env` (gitignored) or Secret
  Manager in prod. Nothing hardcoded, nothing committed. `.env.example` documents every
  variable with no real values.

## Success Criteria

Maps directly to the 10 test scenarios in the originating spec (student adds colleges →
both researched; 0-recommendations conflict → minimum feasible plan identified; strong
essay match → high score; superficial match → lowered confidence + explained gap; near
deadline + near-complete → high priority; far deadline + long remaining work → priority
rises appropriately; distant deadline but long recommender lead time → priority agent
still flags it; stale/unreliable source → flagged, verification requested; partial
progress without upload → representable; two colleges, similar requirements, different
recommender preferences → distinguished, not conflated). These become the
`agents-cli eval` dataset in Milestone 15 — see `Non-Functional Requirements` below.

## Architecture & Sub-Agents

**Monorepo layout** (single Cloud Run service hosting the ADK app + custom REST routes;
one static-hosted React frontend):

```
collegentic/
  agent/                     # `agents-cli scaffold create agent --agent adk ...`
    app/
      agent.py                # orchestrator + pipeline + all sub-agents
      config.py                # models, thresholds (mirrors deep-search's ResearchConfiguration)
      schemas.py                # Pydantic: College, Requirement, ResearchSource, Essay,
                                 #   EssayPrompt, EssayMatch, Task, Recommendation, Conflict,
                                 #   Readiness, AgentRun, PendingAction
      tools/
        firestore_tools.py
        scoring.py               # compute_priority_score / compute_readiness_score
      callbacks.py               # agent-activity logging (before/after_agent_callback,
                                 #   adapted from deep-search's collect_research_sources_callback)
                                 #   + source-collection callback for the Research Agent
      fast_api_app.py            # generated by scaffold; extended with our REST routes
                                 #   (colleges/tasks/essays CRUD, /api/demo/seed,
                                 #   /api/pending-actions/{id}/approve|reject)
    tests/
      eval/datasets/            # the 10 scenarios above, agents-cli eval format
      test_runnability.py
    .env.example
  frontend/                  # Vite + React + TS, Tailwind + shadcn/ui base (per deep-search),
                              # restyled to navy/orange design tokens — no chat-first UI
    src/
      pages/  components/  lib/api.ts  lib/theme.ts
  docs/
    architecture-diagram.md   # Mermaid, rendered in README
  .agents-cli-spec.md
  README.md
```

**Why one Python service:** avoids a second backend just to host CRUD routes — the ADK
scaffold already generates a FastAPI app; we extend it. Matches "do not introduce
unnecessary infrastructure."

**Pipeline (SequentialAgent, adapted from `deep-search`'s `research_pipeline` shape):**

```
orchestrator_agent (root LlmAgent)
  tools: get_tracked_colleges
  - parses NL college input -> normalized names (google_search only if a name is ambiguous)
  - diffs against tracked colleges -> new_colleges[]
  - on new_colleges present, delegates to college_intake_pipeline (sub_agent transfer,
    exactly like deep-search's interactive_planner_agent -> research_pipeline)

college_intake_pipeline (SequentialAgent) — steps 0-2 built in Milestones 3-4, in this
  corrected order (originally drafted as research -> structure -> confidence loop; the
  loop must run BEFORE structuring, evaluating raw prose findings the same way
  deep-search's research_evaluator grades section_research_findings, not the already-
  structured output — a structured-output agent can't also hold open-ended tools to
  re-search with):
  0. college_intake_agent (custom BaseAgent, no LLM) — built in Milestone 4, ahead of
     schedule: the Requirements Agent needs a real Firestore college_id to write into.
     Ensures a College doc exists per requested name (reusing an existing one by
     name/alias match), sets `college_name_to_id` + `new_college_names`. This is the
     "identify new schools" bookkeeping originally attributed only to the Orchestrator
     (Milestone 5) — that agent will drive `requested_colleges` from parsed
     natural-language input and reuse this step as-is.
  1. college_research_agent (LlmAgent, tools=[google_search]) — built in Milestone 3
       - one call handles the full new_colleges[] list (multi-query search per college,
         same "N queries per goal" pattern as deep-search's section_researcher); output
         is structured with a `## <College Name>` header per college so step 2 can split
         it reliably
       - after_agent_callback: collect_research_sources_callback (adapted) populates
         `state["sources"]` / `state["url_to_short_id"]` ONLY — it does not write
         ResearchSource docs. Revised from the original plan below: college attribution
         for a source isn't knowable until requirements are structured per-college, so
         persistence moves to step 2. Also found live: Gemini's grounding metadata often
         leaves `chunk.web.domain` unset (title carries the domain string instead), AND
         `chunk.web.uri` is an opaque `vertexaisearch.cloud.google.com/grounding-api-redirect/...`
         link, never the real page URL (Milestone 4 finding — confirmed by inspecting
         real persisted data). Neither `url` nor `domain` is usable for official/secondary
         classification; `title` is the only reliable signal (it holds the bare domain
         string, e.g. "rice.edu", when Gemini has no better page title) — see
         requirements_agent.py's `_is_official_source`.
       - output_key: raw_research_findings
  2. requirements_agent (LlmAgent, output_schema=RequirementsExtraction, no search)
       - normalizes raw_research_findings -> Requirement docs (Firestore write tool),
         and — per the revision above — is also the step that persists ResearchSource
         docs, now that each source can be attributed to the right college. Runs once,
         AFTER a confidence-refinement loop (not before, as originally drafted) — see
         Milestone 4 note below.
       - output_key: extracted_requirements
       - built as requirements_pipeline = SequentialAgent([requirements_confidence_loop,
         requirements_agent]) — the loop (below) runs first, once per this whole
         sub-pipeline's invocation, THEN requirements_agent structures the refined result.
     requirements_confidence_loop (LoopAgent, max_iterations=2, runs BEFORE step 2 above)
       - findings_evaluator (LlmAgent, output_schema=Feedback: pass/fail + follow-up
         queries, grades the RAW prose findings) — adapted from deep-search's
         research_evaluator
       - EscalationChecker (custom BaseAgent, identical pattern to deep-search's) — stops
         the loop once grade == "pass"
       - findings_followup_search (LlmAgent, tools=[google_search]) — runs the follow-up
         queries, merges new findings into raw_research_findings (same `##` header
         structure), re-collects sources via the same callback as step 1
  3. cross_college_analysis (ParallelAgent)
       - conflict_agent (LlmAgent, no search; reads all tracked colleges' Requirements +
         Recommendations) -> Conflict docs
       - essay_matching_agent (LlmAgent, no search; reads EssayPrompts + StudentMaterials)
         -> EssayMatch docs
  4. deadline_priority_agent — wraps compute_priority_score (deterministic) per task/
     requirement, LLM composes the explanation string only
  5. task_planning_agent (LlmAgent) — reads Requirements + Conflicts + EssayMatches +
     existing Tasks (dedupe check) -> new Task docs; anything that would alter/overwrite
     user-authored material goes to create_pending_action instead of a direct write
  6. readiness_agent — wraps compute_readiness_score (deterministic) per college, LLM
     composes the explanation string only

student_advisor_agent (separate root LlmAgent, invoked on demand — NOT part of the
  pipeline) — read-only Firestore tools, no google_search, no write tools.
```

Every sub-agent gets `before_agent_callback`/`after_agent_callback` = the shared activity
logger, writing/updating an `AgentRun` doc (`running` → `completed`/`failed`) keyed by a
`pipelineRunId` so the Agent Activity page can group one intake run.

**HITL implementation choice (deviation from the `ambient-expense-agent` recipe, stated
explicitly):** that recipe pauses execution mid-graph via ADK 2.0's `RequestInput`, which
depends on in-memory session state surviving until a human resumes it (its own AGENTS.md
flags this as fragile across restarts). Collegentic's UI is dashboard-driven, not a single
long chat session, and approvals may happen minutes or hours after a pipeline run
finishes. So instead: agents that want to take an approval-gated action call
`create_pending_action(...)` (a normal Firestore write, not a graph pause) and continue;
the pipeline does not block on it. The frontend's Approve/Reject buttons hit
`POST /api/pending-actions/{id}/approve|reject`, which then performs the actual write.
This is simpler, durable across restarts, and fits a dashboard UX better — noted as an
explicit architectural deviation, not an oversight.

**Not built as a runtime agent:** the spec's "Evaluation Agent" is treated as the
`agents-cli eval` LLM-judge harness (Milestone 15), not an 11th live agent students
interact with — there's no user-facing task for a 10th pipeline stage to do at runtime.
Flagging this as an assumption; open to reversal if the user wants a literal runtime
agent instead.

## Data Sources & Auth

- **Gemini**: `gemini-3.6-flash` for every agent by default (worker and critic model both
  — see Constraints; this is the scaffold's current default, newer than the `deep-search`
  recipe's `gemini-3.5-flash` — trusted over the recipe per the "don't guess model names
  from training data" rule). Vertex AI via ADC — confirmed working against the
  `collegentic-hackathon` GCP project (billing linked, Vertex AI API enabled) in Milestone 1.
- **Firestore**: single database, collections scoped under `users/{userId}/...` (see
  schema below). No Google auth yet — `userId` is a client-generated UUID persisted in
  `localStorage`, sent as a header. This is an explicit MVP assumption (Google OAuth is
  an out-of-scope future extension per the spec); it's the seam future OAuth replaces.
- **Web research**: ADK's built-in `google_search` tool (Gemini grounding), no separate
  Search API key needed — same as `deep-search`.
- **Cloud Run**: `min_instance_count = 0`, small `max_instance_count` (e.g. 3), 512Mi–1Gi
  / 1 vCPU. No GKE, no Agent Runtime, no vector DB, no Pub/Sub — none of those are needed
  for a request/response, dashboard-driven product.

## Firestore Schema

```
users/{userId}
  mode: "live" | "demo"
  applicationYear: number
  createdAt

users/{userId}/colleges/{collegeId}
  name, aliases[], applicationType, schoolColors{primary,secondary}, logoUrl
  status: Planning|InProgress|Ready|Submitted
  deadlines: { EA?, ED?, RD?, financialAid? }
  readiness: { score, breakdown{requirements,essays,recommendations,testing,deadline},
               explanation, computedAt }
  priority: number
  lastResearchedAt

users/{userId}/colleges/{collegeId}/requirements/{requirementId}
  type, description, required: bool
  status: NotStarted|Planning|InProgress|NearlyComplete|Complete|Submitted|Verified
  completionPercentage, deadline, dependencies: [requirementId]
  category, confidence: high|medium|low, needsVerification: bool
  sourceIds: [sourceId]

users/{userId}/researchSources/{sourceId}
  collegeId, url, title, dateResearched, official: bool, confidence, excerpt

users/{userId}/materials/{materialId}          # essays/activities/notes — never edited by agents
  title, type: CommonApp|Supplemental|ActivityDescription|Award|Note|Idea
  topic, description, partialText, completionPercentage, wordCount, themes[]
  status: NotStarted|Idea|Drafting|InProgress|NearlyComplete|Complete|Submitted
  createdAt, updatedAt

users/{userId}/colleges/{collegeId}/essayPrompts/{promptId}
  text, wordLimit, required: bool, category, requirementId

users/{userId}/essayMatches/{matchId}
  promptId, collegeId, materialId, matchScore, sharedThemes[]
  recommendation: adapt|new, reasoning, computedAt

users/{userId}/tasks/{taskId}
  title, description, collegeId, category, deadline, estimatedMinutes
  status: NotStarted|InProgress|Blocked|Done
  priorityScore, priorityExplanation, dependencies: [taskId]
  sourceRequirementId, createdBy: agent|user, createdAt

users/{userId}/recommendations/{recId}
  recommenderName?, recommenderType: STEM|Humanities|Counselor|Other
  status: NotIdentified|Planned|Requested|Received|Verified
  collegeIds: [collegeId], requestedAt

users/{userId}/conflicts/{conflictId}
  type: recommendation|essay|deadline|testing|financialAid
  collegeIds: [collegeId], description, recommendation, severity
  relatedRequirementIds: [requirementId], status: open|acknowledged|resolved

users/{userId}/agentRuns/{runId}
  pipelineRunId, agentName, status: running|completed|waiting_for_user|failed
  startedAt, completedAt, summary, relatedCollegeIds[], errorMessage?

users/{userId}/pendingActions/{actionId}
  type, description, proposedChange: json, status: pending|approved|rejected
  createdByAgent, createdAt, resolvedAt
```

Every `Requirement` links to `sourceIds`; every `EssayMatch` links `promptId` +
`materialId`; every `Task` links `sourceRequirementId` and optional `dependencies`; every
`Conflict` links `relatedRequirementIds` — satisfying the "many-to-many, source
transparency, dependencies" requirements without a graph DB.

## Frontend Structure

Sidebar pages (per spec's suggested nav, adopted as-is): Dashboard, Colleges,
Requirements, Essays, Tasks, Priorities, Essay Map, Application Readiness, Agent Activity,
Settings. Onboarding is a pre-sidebar full-screen route (`/onboarding`) shown when no
colleges are tracked and demo mode is off. The Student Advisor is a persistent
slide-over chat panel reachable from a top-bar button on every page, not its own sidebar
entry — it's a cross-cutting explainer, not a distinct tool. Stated as a UX judgment call;
easy to promote to a full page later if it doesn't work in practice.

Design tokens: navy primary, orange accent, gradients limited to hero/activity-indicator
use, no glassmorphism, no oversized rounded cards, tables/lists as the default dashboard
layout (per spec section 4–6).

## Non-Functional Requirements

- Eval dataset (Milestone 15) encodes the 10 test scenarios from `Success Criteria` as
  `agents-cli eval` LLM-judge cases, not pytest. Pytest covers `scoring.py`'s deterministic
  formulas and Firestore tool schema validation only.
- Every agent name is treated as a public contract with the frontend's Agent Activity
  feed (same gotcha as `deep-search`) — renaming a sub-agent requires updating the
  frontend's activity-label mapping in the same change.
- README must be reproducible by someone who has never used GCP/ADK (per spec section 33)
  — deferred to Milestone 18.
